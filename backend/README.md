# OBD Diagnostic Report backend

## Requirements

- Node.js 20 or newer
- A Gemini API key with access to the Gemini API

## Setup

```bash
cd obd-report-backend
npm install
```

Copy `.env.example` to `.env`, then set `GEMINI_API_KEY`. Keep the key on the server; do not put it in frontend code.

```bash
npm start
```

Open <http://localhost:4000>. The server also exposes `GET /api/health`.

The upload endpoint accepts TXT, CSV, and LOG files (code extraction runs locally on the server), plus PDF, PNG, JPG, and WEBP files (Gemini reads the attachment). There is no application-level file-size cap. Very large files remain subject to available server memory and Gemini API request limits. Each extracted code is explained dynamically with Gemini. The backend defaults to the stable `gemini-3.6-flash` model and retries temporary rate-limit or service errors. The PDF report is then generated by the server.

## Endpoints

- `POST /api/analyze-file` — multipart form with a `file` field; returns extracted codes and explanations.
- `POST /api/obd/lookup` — JSON `{ "code": "P0300" }`; returns one explanation.
- `POST /api/reports` — JSON `{ "name": "...", "phone": "...", "codes": ["P0300"] }`; performs server-side lookups, allocates a SQLite auto-increment ID, writes the PDF, and returns `downloadUrl`.
- `GET /reports/:fileName` — downloads a generated PDF.

## Persistence and deployment

The monotonically increasing report ID is stored in `DATA_DIR/report-counter.json`; generated PDFs are stored in `DATA_DIR/reports`. The counter persists across restarts and requests are serialized within this Node process. Use one backend instance with persistent `DATA_DIR`; for multiple instances, replace the counter with an atomic sequence in a shared database. Configure `FRONTEND_ORIGIN`, `PUBLIC_BASE_URL`, `GEMINI_MODEL`, and secrets through the deployment environment. Use HTTPS in production.
